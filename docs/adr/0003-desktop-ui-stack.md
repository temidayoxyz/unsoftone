# ADR-0003: Desktop UI stack — hybrid webview chrome with a Rust rendering core

- Status: Accepted (provisional — must be validated by the Phase 0 spike)
- Date: 2026-10-07

## Context

An office application has two very different halves, and conflating them is the
most common architectural mistake in this space.

**Application chrome** — ribbon, menus, toolbars, sidebars, dialogs, settings,
inspectors. This is a large number of conventional controls with conventional
behaviour. HTML/CSS is excellent at this. Rust GUI toolkits are mediocre at it.

**Document canvas** — thousands of shaped glyph runs, caret hit-testing inside
bidirectional text, selection rectangles, custom scrolling, tables and images at
arbitrary positions. This is where a DOM fights you, and where `contenteditable`
is actively harmful because it imposes a document model that is not a document
model.

A third concern dominates everything: **the input method editor (IME).** Placing a
caret correctly inside shaped, bidirectional text while a user composes CJK or
Indic input requires the platform IME, including candidate-window positioning
and preedit handling. A webview provides this almost for free through a hidden
editable element. A hand-rolled GPU text renderer does not — you must implement it
yourself, badly at first, forever.

Accessibility is the fourth concern. `accesskit` (27M+ downloads, actively
maintained, with a winit adapter) is solid for native Rust GUIs. Webview
accessibility quality varies by platform and is weakest on Linux/WebKitGTK.

## Decision

**Hybrid: webview for chrome, Rust for the document.**

- `Tauri` v2 (or `wry` directly) hosts application chrome.
- The document view is a **canvas surface** driven by a Rust layout engine.
- Text input is anchored by a **hidden editable element** positioned over the
  caret, which supplies native IME, selection and accessibility.
- The Rust core owns the document model, layout, rendering and all file I/O.

**This decision is provisional.** It must be validated by the Phase 0 spike
before we build on it. The spike is throwaway; only its findings survive.

### Spike exit criteria

1. A document containing RTL text, CJK, tables and images lays out correctly and
   scrolls at interactive speed.
2. A caret blinks in the right place and moves correctly with arrow keys through
   mixed-direction text.
3. **A CJK IME works** — candidate window appears in the right place, preedit
   renders inline, and commit lands at the correct caret offset.
4. Screen-reader output is acceptable for basic document reading.

If criterion 3 fails, that is the finding that matters, and it may force a
different stack.

## Consequences

**Easier:** chrome is cheap and looks good quickly; native IME comes almost free;
hiring and contributor familiarity is far better than any Rust GUI toolkit.

**Harder:** two runtimes and a boundary between them that must be designed
carefully; a hand-rolled canvas renderer; accessibility quality limited by the
webview on some platforms; the hidden-editable-element technique is genuinely
fiddly and has sharp edges. This is the largest technical risk in the project and
is exactly why the spike comes before the architecture.

**Forecloses:** access to a mature native text-input stack other than the
webview's. This is the real cost, and the spike is how we price it.

## Alternatives considered

**Native Rust GUI only — `egui`/`iced`.** Rejected: immediate-mode design is a
poor fit for a large, stateful document editor; text editing and accessibility
are weak. Excellent for tools and debug UIs; wrong for this.

**`Slint`.** Rejected: declarative and pleasant, but the text-editing story is
too thin for a word processor.

**Native Rust GUI with hand-rolled IME.** Rejected for now: owning the IME on
three platforms is a project in itself, and it is the exact complexity the
webview removes. Revisit only if the spike proves the webview unworkable.

**Write the chrome in a native toolkit and the canvas in WGPU, with no webview.**
Rejected for the IME reason above.

**Full custom rendering including layout, delegated to no library.** Rejected:
contrary to [ADR-0002](0002-text-layout-parley.md); we do not reimplement
HarfBuzz.

## Review trigger

If the spike fails criterion 3 (IME), this ADR is superseded. Write the
replacement; do not edit this file.
